The constraint

You cannot do this over Bluetooth

macOS implements the Bluetooth A2DP source role only. It has no sink. Your Mac will never appear in a phone's Bluetooth output list as a speaker, and there is no setting that changes it.

So the audio takes a different road — over ADB, by USB cable or Wi-Fi — and arrives at the Mac as a normal audio stream.

Phone→ USB / Wi-Fi→ scrcpy→ CoreAudio→ Headphones

Measurements, not estimates

This project exists because of a latency budget, so nothing in it is guessed.

QuantityValueHow
Mac → AirPods Max, Bluetooth 170.7 ms CoreAudio reported device latency
Wi-Fi jitter to phone 6–21 ms 20 ping packets, σ 3.6 ms
Wi-Fi buffer floor 200 ms 150 ms ran clean twice, then lost 514 ms of audio on the third run
Wired buffer 15 ms Chosen for a jitter-free link; validated by listening, not instrumented
One honest caveat. The 15 ms wired buffer is below scrcpy's own 50 ms default and was confirmed by ear rather than by counting dropped samples. If you hear clicks, that is sample-skipping — raise it with --buffer. It sounds like glitches, not lag.
What it does not do

Limits worth knowing first

Phone calls won't capture

Android blocks voice communication from playback capture, and there is no return mic path.

Video on the phone leads

The phone doesn't know its audio was captured, so it never delays video to compensate.

Some apps opt out

Apps can refuse audio capture. Instagram allows it; Spotify does not.

The watchdog isn't a pin

scrcpy can't target a device, so playback stops within ~0.5 s of the output changing — not instantly.
